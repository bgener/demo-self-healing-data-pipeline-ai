"Build a Production ELT Pipeline with Airbyte, dbt, and Dagster\n\nYour e-commerce app runs on Microsoft DocumentDB. Orders come in as nested JSON documents with line items, shipping info, and payments in five currencies including Bitcoin and Ethereum. Leadership wants hourly analytics dashboards. The current approach: a Python script that a senior engineer wrote two years ago, running on a cron job, breaking every time someone adds a field to the order schema.\n\nYou could rewrite that script. Or you could build a pipeline where every piece is a separate, testable, replaceable component: extraction, loading, transformation, orchestration. Where schema changes propagate automatically. Where you know exactly how fresh your data is and get alerted when it goes stale. Where the entire configuration lives in version control and deploys through Terraform.\n\nThat is what we are building. A complete ELT pipeline that pulls data from two sources (a NoSQL database and a REST API), loads it into a columnar analytics engine, transforms and enriches it with SQL, and orchestrates the whole thing with freshness guarantees. Everything runs locally in Docker. Everything is tested in CI.\n\n---\n\n What Is the Modern ELT Stack?\n\nETL (Extract, Transform, Load) dominated for decades. You transformed data before loading it into the warehouse. The problem: every new business question meant a new transformation pipeline. The warehouse never had the raw data, so you could not go back and re-transform.\n\nELT flips the order. Load the raw data first, then transform it inside the warehouse. The warehouse is cheap and fast enough to handle it. This gives you lineage, replayability, and the ability to add new transformations without re-extracting.\n\nThe stack we are using splits each concern into a dedicated tool:\n\n Tool  Role  Why this one \n---------\n **Airbyte**  Extract and load  300+ connectors, handles schema drift, open source \n **dbt**  Transform  SQL-based, version-controlled, built-in testing and docs \n **Dagster**  Orchestrate  Asset-based (not task-based), freshness policies, observability \n **Terraform**  Configure  Airbyte connections as code, no manual UI clicking \n **ClickHouse**  Store and query  Columnar, fast analytical queries, handles nested JSON \n\nCompare this to the alternatives:\n\n Approach  Pros  Cons \n---------\n Custom scripts (Python/C)  Full control  No lineage, no freshness, breaks on schema changes \n SSIS  Mature, enterprise  Windows-only, XML configs, painful to version-control \n Azure Data Factory  Managed, scalable  Vendor lock-in, expensive at scale, GUI-driven \n Airflow + custom operators  Flexible  Task-based (not asset-based), DAG complexity grows fast \n **Airbyte + dbt + Dagster**  **Modular, testable, open source**  **More moving parts to set up initially** \n\nThe trade-off is real: more components means more setup. But each component is replaceable. Outgrow Airbyte? Swap it for Fivetran. Prefer Snowflake over ClickHouse? Change the dbt adapter. The interfaces between components are stable.\n\n---\n\n The Demo Scenario\n\nWe have an e-commerce platform backed by Microsoft DocumentDB, the open-source engine behind Azure Cosmos DB's vCore offering. But it has three limitations that the ELT pipeline solves:\n\n1. **No cross-source enrichment.** The aggregation cannot join with CoinGecko prices to convert BTC revenue to USD. The database only sees its own data.\n2. **No deduplication across syncs.** If you run this query at different times, you get different results. There is no concept of \"the latest version of each record.\"\n3. **Wrong tool for dashboards.** DocumentDB is optimized for transactional workloads. Running heavy aggregations against it competes with production traffic. ClickHouse handles analytical queries without touching the source.\n\nThe pipeline does not replace the aggregation. It complements it by adding what a single database cannot do alone.\n\n---\n\n Configuring Airbyte with Terraform\n\nAirbyte extracts data from sources and loads it into destinations. The staging models parse this into relational columns.\n\nThe core challenge is the nested  array. Each order can have 1 to 5 line items. We need one row per line item for analytics. Unlike Airflow's task-based DAGs, Dagster thinks in **assets**: each dbt model and each Airbyte sync is an asset with a known state, a last-materialized timestamp, and optional freshness requirements.\n\n Defining assets\n\nThe  and  integrations map external resources to Dagster assets automatically:\n\n Freshness policies\n\nThe  on the DocumentDB assets means: if the orders data is older than 60 minutes, mark it as overdue. The Dagster UI shows a clear indicator: green for fresh, yellow for approaching the SLA, red for stale.\n\nCrypto prices have a tighter SLA: 15 minutes. If the CoinGecko sync fails or slows down, you see it immediately in the asset graph.\n\n Scheduling\n\nA single hourly schedule triggers the full pipeline:\n\nDagster handles the dependency graph. It runs Airbyte syncs first, then dbt models in the correct order (staging before intermediate before marts). If the Airbyte sync fails, the dbt models do not run. If a single dbt model fails, downstream models are skipped.\n\n---\n\n Testing the Pipeline in CI\n\nThe pipeline integration test is the most important piece.
